# Inbox architecture
- ChatTypography uses shared semantic sizes for names, previews, tabs and headers; timestamp tracks stay unchanged. Channel toggles/counts belong only in the open lead header, and SwipeChatCard owns between-row dividers without list enclosure frames. Why: matching tabs and uncluttered previews.
- Chat-origin lead saves reopen the saved conversation; first official outreach requires the exact approved opt-in template and a service-only workspace/phone claim, never retrying ambiguous sends. Green avatar jobs authorize and scope reads/writes by workspace and unchanged phone. Why: prevent duplicate outreach and cross-tenant photos.
- WhatsApp media authorization comes from a visible source message; credentials match its receiving phone, never an unrelated latest provider. Unavailable attachments remain inline and media responses are private. Why: prevent token mismatch, media leaks and blank error states.
- Hero tabs use the URL; panes stay mounted and contextual add events reach only the active pane. useInboxFavorites owns account/workspace-keyed favorites, with RLS rechecking target access on read/write. Why: isolated navigation and persistent saves.
- Hero search/favorites events reach only the active mounted pane and search state is reported back; orphan chat stars target the authorized source message, never a synthetic phone ID. Why: consistent controls without creating client identities.
- Lead chat names/avatars reuse the authorized LeadCRM details sheet embedded in the inbox; community identities remain public-profile links. Header menus persist hidden to preserve nested dialogs and close on action clicks; saved-chat removal requires confirmation and favorites replace pane content. Channel visibility is per-chat default-on exclusion state. Why: preserve editing, dialogs and truthful independent filtering.
- Bubbles use physical outgoing-left/incoming-right alignment. Receipt RPCs authorize recipients; visible active panes acknowledge reads, fetched messages delivery. Transition-only receipt doorbells refetch receipts, not messages; provider metadata alone determines external outbound status. Why: truthful ticks without notification loops.
- Lead identity clicks open authorized full details; the top profile icon opens /lead-profile/:leadId with history-entry return selection. This separate lead projection uses lead_profile_access, never account UUID lookup. Community profiles stay unchanged. Why: safe identity and exact return.
- Keep lead chats and account-participant community chats separate; preserve mounted tab state and use private data-free per-user Realtime notifications with authorized refetches. Why: instant updates without publishing private rows or borrowing workspace identities.
- Rita count/filter share effective global/per-lead state; SwipeChatCard owns gesture actions without retaining exiting rows. Community removal hides only the caller's card and disables their autopilot; groups restrict autopilot to owners. Auth-bound settings dispatch incoming-message jobs to rita-conversation with unique source claims and fresh authorization checks. Why: accurate counts, no destructive peer deletion, impersonation or duplicate AI replies.
- Group rosters authorize group data and Rita context; assistant logs are server-written, shared only with conversation participants, and never include private workspace CRM/tools in community replies. Why: prevent impersonation and cross-workspace disclosure.
- Broadcast posts (including Rita) require the group owner; unread cursors advance only to displayed messages in a visible active group via an auth-bound RPC. Why: prevent subscriber publishing and premature unread clearing.- Member pickers and new direct chats use CommunityDirectory (auth-bound community_directory RPC with server-derived role categories); eligibility includes brokers, developers and partners. Why: one searchable, role-badged directory.
- In the new-chat directory the name/avatar row opens the public profile and a chat starts only from the explicit "שיחה" action. Why: users check who they are messaging before opening a chat.
- Community blocks live in community_user_blocks; the private-message insert policy rejects blocked senders and group messages from blocked users are hidden client-side. Contact identity comes from community_profile_cards. Why: server-enforced blocking without exposing other users' block lists.
- Public profiles use /community/profile/:userId without PageHero, with a local Close and server-redacted board assets; avatars open profiles, row bodies open chats. Inbox section stays in URL and scroll owners retain history positions. Full-screen avatar previews opt out of dialog width limits. Why: accurate profile returns and private pricing.
- Public community profiles list only published, live, undistribution-paused listings via community_profile_listings; partnership terms live in community_deal_terms readable by both participants. Why: safe co-brokerage discovery and documented deals.
- Public bio is separate from private Rita persona text; source bios never overwrite custom bio. Office discovery matches saved brokerage and location, and project projections require existing published project listings. Why: prevent private-text disclosure, false affiliations and implicit publication.

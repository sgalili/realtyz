# Broker import queue
- Agency descriptions are parsed from agency-scoped DOM/JSON fields, stored separately from personal bios and backfilled only when the saved office description is null; public office details may reuse a description from an exactly matched same-city colleague. Why: preserve source meaning without overwriting identity or mixing branches.
- Broker discovery enters the agencies directory via leased, service-only Web Unlocker reads; card-scoped personal identity/license and exact listing links feed existing live-checked draft creation, with separate directory cache keys and sequential checkpoints. Why: no office-name impersonation, stale search offsets or public scraping bypass.
- Summary volumes survive DOM/JSON deduplication and checkpoints; known out-of-range cards skip before enrichment, unknown counts remain eligible for inspection. Yad2's directory has no numeric pagination (16 top offices per geography node), so discovery walks a checkpointed topArea→area→city→neighborhood frontier, inspects each office once per job, and enriches offices via their profile payload (identity only from the broker whose license equals the office license, up to ten own ads). The unlocker zone comes from BRIGHTDATA_UNLOCKER_ZONE. Completed/disqualified agency checks suppress detail reads for seven days per canonical agency and configured min/max; failed requests never write registry entries. Why: reduce paid scans without guessing volume, losing pagination or blocking changed criteria.
- Broker chunks remain sequential with a one-second queue gap, without duplicating the transport pacer. Broker and developer 429 responses keep the job running with an adapted backoff and a database-scheduled automatic retry; no manual Continue/reset is required. Discovery page reads have a fifty-second budget and three attempts; unreadable directory pages pause visibly, and developer failures retain per-link errors. Why: bounded progress without false empty results, request bursts or lost checkpoints.
- Web Unlocker REST calls omit sticky session/IP settings and use provider-managed rotation with bounded peer/request diagnostics; Browser fallback reconnects per fetch. Why: supported API semantics without pretending IP uniqueness or 429 prevention is guaranteed.
- Provider requests allow 120s inside a 130s scrape budget and 140s worker-call timeout; structured failure logs redact credentials and bound payloads, and retry uses persisted checkpoints/cache. Why: avoid premature aborts while returning before the platform deadline.
- Discovery uses the existing Yad2 Bright Data parser with a leased Super Admin job, compact source records and individual detail enrichment; public/search reads retain their existing cache gates. Why: reuse exact-source attribution without broad scraping privileges.
- Database-triggered steps persist per-broker/per-listing checkpoints, atomically lease and control jobs, and stop between external actions; pause never cancels an already submitted save. Why: modal-independent progress and safe resume.
- Only current Super Admin-created accounts without first login may be reused; ads are unpublished drafts; only explicit "gone" status skips an ad, unknown status continues with a soft warning and missing identity is never invented. Why: prevent account takeover and false publication.
- Registry checks require exact license and person match; any fallback approval is tied to job, administrator, user and license and remains distinct from official verification. Why: prevent borrowed broker identities.- Search pages and ad details are read through the service-only scrape cache with fixed TTLs measured from fetch time (never extended on read); empty/failed fetches are never cached, and live-status checks and imports always go live. Why: avoid repeat Bright Data spend without stale activity or publication.
- Imported brokers are grouped by license; a hidden Yad2 mobile creates the account as pending_contact with a .invalid placeholder email, completed only through Super Admin admin-broker-contact (pre-first-login, uniqueness-checked) before any invitation. Why: import without inventing identity or contacting anyone automatically.
- Every broker-import draft (directory and pasted links) passes residential_only to yad2-unlocker, which rejects non sale/rent or commercial/office/shop/land/industry ads before saving; the queue skips them like other unavailable ads. Why: import only residential sale/rent inventory.
- Pasted broker/office profile links use parseAgencyProfile (page-level identity, own non-related residential item links, cache key includes the per-link limit). Why: profile pages are not directory cards.
- Pasted-link jobs (source 'urls') run in instant mode: no provider gap and no per-ad status pre-check; automatic 429 backoff and the residential/availability save checks still apply. Why: trusted explicit links, fast results.
- Developer links use per-page developer/project checkpoints and exact canonical source URLs; every discovered own project page is merged with all extracted buildings/units, and the expected-project input is only a completeness warning; only an explicit Super Admin max_projects caps to the first N projects in source order (their full inventory still imports). Normal saves self-schedule the next step; transient failures and 429s keep the job running and arm a one-off delayed retry, with no Continue/reset controls. Permanent configuration or identity failures end visibly as failed rather than pretending success. Why: comprehensive unattended imports without invented projects, tight retry loops or false completion.
- Imported developers are active silent accounts with no broker-license requirement, created without phone/email/invitation when absent and granted only the developer role; exact existing developer-source links are reused, then the single developer already owning a scanned source project, then a unique exact company name; never phone-only account matching. Projects save privately under that developer's own workspace with manual edits, commission settings and existing publication state preserved. Why: license-appropriate onboarding without account takeover, messages or accidental publication.

- Automatic developer discovery reads only leased canonical Yad2 developer-directory pages, then reuses the normal per-profile queue and project cap. Normalized company names are an identity fallback after source/project ownership, selecting the oldest existing account. Why: autonomous discovery without duplicate developer workspaces.
- Directory scans keep an append-only broker list and save each newly found broker as a draft immediately (resumePhase returns to the same discovery checkpoint); offices are filtered only by the minimum ad count, while the maximum caps saved ads per broker. Why: paused scans keep every found broker and large offices are not discarded.
